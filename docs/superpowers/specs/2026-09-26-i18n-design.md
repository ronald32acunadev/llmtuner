# Internationalization (English + Spanish) — Design

Date: 2026-09-26
Status: approved in conversation, pending written review

## Goal

Make LLM Tuner publishable for a non-Spanish audience. The app must work in **English and Spanish**, with **English as the default and the base language** of the codebase. Spanish becomes a translation, not the source.

## Decisions

| Topic | Decision |
|---|---|
| Languages | `en`, `es`. No plans for more now; the design does not prevent adding them. |
| Default | `en`. |
| Selection | Manual only. No detection from OS or browser locale. |
| Persistence | `settings.json` in the app's config dir, shared by CLI, web and Electron. Not `localStorage` (Electron uses a random port, so the origin changes on every launch). |
| Base language | All code, identifiers, source strings and catalog keys are English. Missing Spanish text falls back to English. |
| Core output | `src/core` emits codes + params, never translated text. Each interface translates. |
| Library | None. Plain JS catalogs and a small `t()` function. |
| Docs | `README.md` in English + `README.es.md` in Spanish. `docs/PROYECTO.md` and `CLAUDE.md` translated to English. |

## Architecture

### `src/i18n/` (new, no dependencies, runs in Node and the browser)

- `en.js`, `es.js`: each default-exports a flat-namespaced object. Keys are grouped by area with dot notation: `engine.*`, `status.*`, `errors.*`, `install.*`, `bench.*`, `cli.*`, `web.*`. Values may contain `{param}` placeholders.
- `index.js` exports:
  - `LOCALES = ['en', 'es']`
  - `DEFAULT_LOCALE = 'en'`
  - `CATALOGS = { en, es }`
  - `t(locale, key, params = {})`: looks up `key` in the locale's catalog, falls back to `en`, and if still missing returns `key` itself (so gaps are visible, never silent). Replaces every `{name}` with `params.name`; unknown placeholders are left as-is.
  - `normalizeLocale(value)`: returns `value` if it is in `LOCALES`, else `DEFAULT_LOCALE`.

The pure helpers (`LOCALES`, `DEFAULT_LOCALE`, `normalizeLocale`, `format`) live in `src/i18n/core.js`, which has no imports. `index.js` re-exports them and adds the catalogs. The browser fetches the merged catalog through `GET /api/i18n/:lang` (JSON, English filling gaps) and imports `format` from `/i18n/core.js`, which `src/web/server.js` serves as a static ES module. Nothing else under `src/i18n` is exposed.

### `src/core` changes

`src/core` stops producing user-facing text. Every user-facing string (~30 sites in `tuner.js`, `engines/lmstudio.js`, `engines/ollama.js`, `installer.js`, `estimator.js`, `hardware.js`, `llama-server.js`) becomes a code:

- `detectEngines()` returns `reasonCode` + `reasonParams` instead of `reason`.
- `Tuner#log('status', …)` events carry `{ code, params }` instead of `{ message }`.
- User-facing errors throw `new TunerError(code, params)`.
  - `TunerError extends Error`, sets `name = 'TunerError'`, `.code`, `.params`, and `.message = t('en', code, params)` so logs and unknown consumers still get readable English.
  - Lives in `src/core/errors.js`, exported from `src/core/index.js`.
  - `src/core` may import `src/i18n` only for this English `message`. It never reads the user's locale.
- Installer plans: `label` → `labelCode` (+ `labelParams` when needed).
- Benchmark/load results: `note` → `noteCode`; failures we generate carry `errorCode` + `errorParams` beside an English `error` (helper `benchError(code, params)` in `src/core/errors.js`). Raw tool output stays in `error` only.
- `apply()` results: `changes` becomes an array of `{ code, params }`.
- Internal or technical errors stay as plain English text and are not translated: GGUF parse errors (already English), raw output from external tools (e.g. `ollama create` stderr), and similar. Showing the tool's own output is more useful than translating it. Existing Spanish technical messages of this kind are rewritten in English.

### `src/core/settings.js` (new)

- `settingsPath()`: `<config base>/llm-tuner/settings.json`, same base as `presetsDir()`. The base-dir logic is extracted from `presets.js` into a shared `configDir()` in `util.js` so both use it.
- `readSettings()`: returns `{ lang }`. Missing file, invalid JSON or unknown `lang` → `{ lang: 'en' }`. Never throws.
- `writeSettings(patch)`: merges `patch` into current settings, normalizes `lang`, creates the directory if needed, writes the file.
- The path can be overridden with the `LLM_TUNER_CONFIG_DIR` environment variable (used by tests).

## Interfaces

### CLI (`src/cli/index.js`)

- New option `--lang <en|es>`: sets the language for this run **and** saves it with `writeSettings`. An invalid value prints an error (in English) listing valid values and exits with code 1.
- Without `--lang`, the language comes from `readSettings()`.
- Every user-facing string, including `--help`, goes through `t(lang, …)`.
- Core events and `TunerError`s are rendered with `t(lang, code, params)`. Non-`TunerError` errors print their `message` as-is.

### Web server (`src/web/server.js`)

- `GET /api/settings` → `{ lang, locales }`.
- `POST /api/settings` with `{ lang }` → validates, saves, returns the new settings. Unknown `lang` → 400 with `code: 'errors.unknownLocale'`.
- `GET /api/i18n/:lang` → catalog JSON for that locale (404 for unknown).
- `/i18n/index.js` served as a static module (see above).
- API error responses become `{ error, code?, params? }`: `code`/`params` present when the cause is a `TunerError`. Job `finished` events over SSE carry the same fields.
- `/api/state` returns `reasonCode`/`reasonParams` (from `detectEngines`).

### Web UI (`src/web/public/`)

- `index.html`: static text marked with `data-i18n="key"` (text content). The static HTML has no translatable attributes, so no attribute mechanism is added. `<html lang>` is set at startup.
- `app.js` on startup: fetch `/api/settings`, then `/api/i18n/:lang`, apply `data-i18n`, then run the existing `init()`. All strings built in JS go through `t()`, including the SSE progress messages (translated in the browser from `code` + `params`) and API errors (translated when `code` is present, otherwise `error` shown as-is).
- Header gets an **EN / ES** selector. Changing it POSTs `/api/settings` and reloads the page. While a benchmark/load job is running, the selector is disabled so a reload can't cut it off.

### Electron

No changes. It loads the same web UI and therefore uses the same `settings.json`.

## Documentation and project rules

- `README.md` → English. Current Spanish content moves to `README.es.md`. Each links to the other at the top.
- `docs/PROYECTO.md` and `CLAUDE.md` → English, same technical content (formulas, measurements, LM Studio/Ollama internals).
- `CLAUDE.md` rule "La interfaz y los mensajes van en español; el código y los identificadores, en inglés" is replaced by:
  > Code, identifiers and base strings are in English. Every user-facing string goes through `src/i18n` and must exist in both `en` and `es`. `src/core` emits codes, never translated text.

## Testing (`node --test test/`)

New file `test/i18n.test.js`:

1. **Catalog parity:** `en` and `es` have exactly the same keys, and each key has the same set of `{params}` in both.
2. **Code coverage:** scan `src/` (except `src/i18n`) for every quoted string literal that starts with a catalog namespace (`engine.`, `status.`, `errors.`, `install.`, `bench.`, `changes.`, `candidate.`, `common.`, `cli.`, `web.`); every key found must exist in `en`. Keys are therefore always written as full literals, never built dynamically. Adding a string without translating it fails the test.
3. **`t()`:** param substitution; Spanish missing → English; missing in both → key returned; unknown locale → English.
4. **`normalizeLocale`:** valid and invalid values.

New file `test/settings.test.js` (uses a temp dir via `LLM_TUNER_CONFIG_DIR`):

5. Default is `en` when no file exists.
6. Corrupt JSON → `en`, no throw.
7. Unknown `lang` in file → `en`.
8. `writeSettings({ lang: 'es' })` then `readSettings()` → `es`.

Existing `test/core.test.js` must keep passing; any assertion on `reason`/`message` text is changed to assert on the code.

Manual verification:

- `npm start -- --lang es`, then `npm start` (should stay Spanish), then `npm start -- --lang en`.
- `npm start -- --help` in both languages.
- `npm run web`: switch EN/ES in the header, check static text, progress messages and an error.
- `npm run desktop`: opens in the saved language.

## Out of scope

- Languages other than `en`/`es`.
- OS/browser locale auto-detection.
- Translating raw output from external tools.
- Pluralization rules beyond what simple alternate keys can cover.
